**תאריך כתיבה:** 2026-08-17

## 0. סטטוס — קרא לפני הכול

🔴 **שום שלב במסמך הזה טרם בוצע.** נכון לכתיבת שורות אלה:

- **מיגרציות `0031` ו-`0032` טרם הופעלו** על שום מסד נתונים — לא dev ולא prod.
- **חמשת ה-commits טרם נדחפו** ל-remote וטרם נפרסו.

אין לעדכן מסמך זה כך שישתמע שהפריסה או המיגרציות בוצעו, עד שהן אכן יבוצעו.

## 1. למה נדרש חלון תחזוקה — הסיכון של 0031

`0031` **מוחקת** את חתימות ה-RPC הישנות ויוצרת חדשות עם שני פרמטרים נוספים
(`p_privacy_notice_version`, `p_privacy_notice_acknowledged`), **ללא `DEFAULT`**.
PostgREST מזהה פונקציה לפי שמות הארגומנטים בגוף הבקשה — ולכן:

| מצב | תוצאה |
|---|---|
| app ישן + DB ישן | ✅ עובד (בלי acknowledgement) |
| **app ישן + DB אחרי 0031** | 🔴 **שני מסלולי ההזמנה נכשלים** |
| **app חדש + DB ישן** | 🔴 **שני מסלולי ההזמנה נכשלים** |
| app חדש + DB אחרי 0031 | ✅ עובד, acknowledgement נשמר |

**אין סדר פריסה בטוח.** לכן: סוגרים את שער ההזמנות *לפני* שנכנסים למצב מעורב.

`0032` לעומת זאת **בטוחה בכל ארבעת המצבים** (אפס `DROP`, הכל `create or replace`
+ `add column if not exists`, ו-`get_crm_customer` שומרת חתימה וטיפוס החזרה).

**המנגנון:** `NEW_BOOKING_SYSTEM_ENABLED=false` חוסם את שני מסלולי ההזמנה
ב-403 **לפני** כל קריאת RPC, עם הודעה כנה והפניה לוואטסאפ
(`app/api/bookings/request/route.ts`, `app/api/appointments/route.ts`).
כך אף בקשה לא נכשלת ב-500, ואף תור לא נכתב ללא acknowledgement.

## 2א. מדיניות טרנזקציה — שיטה אחת מוכחת

**בפרויקט אין migration runner.** אומת: אין `.github/`, אין CI, אין git hooks,
אין `.husky/`, אין `supabase/config.toml` (רק `supabase/migrations/`), ואין
CLI/driver ב-`package.json`. **שום push אינו מריץ מיגרציה.** ההרצה ידנית.

**לכן לא הוספנו `BEGIN`/`COMMIT` לתוך קובצי ה-SQL** — הטמעה עיוורת הייתה
מתנגשת עם runner שכבר עוטף (ואם יתווסף כזה בעתיד, ההתנגשות הייתה מתגלה רק
בפרודקשן). במקום זאת, הטרנזקציה נאכפת **מבחוץ**.

### 2א.1 — לפני הכול: אימות היסטוריית המיגרציות

🔴 **`psql` ידני אינו מעדכן את `supabase_migrations.schema_migrations`.**
Supabase מנהלת שם את רשימת המיגרציות שהוחלו; הרצה ישירה ב-psql עוקפת אותה
לחלוטין. בלי טיפול מפורש, ההיסטוריה תיראה כאילו 0031/0032 מעולם לא רצו —
וכל `supabase db push` עתידי ינסה להריץ אותן שוב.

**באישור נפרד, לפני כל שינוי DB:**

```bash
supabase migration list --linked
```

* אם הרשימה **אינה מסונכרנת עד 0030** (יש פער, או מיגרציה מקומית שאינה
  מסומנת כ-applied) — 🔴 **עוצרים.** **אין לתקן אוטומטית**, אין להריץ
  `repair` על טווח, ואין להמשיך ל-rollout. זו חקירה נפרדת.
* רק אם הרשימה תואמת עד 0030 — ממשיכים.

### 2א.2 — הרצת המיגרציה (Dockerized psql)

⚠️ **אין להניח ש-`psql` מותקן מקומית.** Docker זמין במחשב, ולכן ההרצה דרך
image רשמי — כך שגם הגרסה של הלקוח ידועה ואחידה.

```bash
docker run --rm -it \
  -v "$PWD/supabase/migrations:/migrations:ro" \
  postgres:16-alpine \
  psql "postgresql://postgres.<PROJECT_REF>@<SESSION_POOLER_HOST>:5432/postgres?sslmode=require" \
    -W \
    --single-transaction \
    -v ON_ERROR_STOP=1 \
    -f /migrations/0031_privacy_notice_ack.sql
```

| רכיב | למה |
|---|---|
| `-v "$PWD/supabase/migrations:/migrations:ro"` | mount **לקריאה בלבד** (`:ro`) — הקונטיינר אינו יכול לשנות את הריפו |
| `--single-transaction` | כל הקובץ בטרנזקציה אחת: all-or-nothing מוכח |
| `-v ON_ERROR_STOP=1` | עצירה בשגיאה הראשונה. **בלעדיו psql ממשיך לשורה הבאה** ומשאיר מצב חלקי |
| `sslmode=require` | חיבור מוצפן בלבד |
| `-W` | **הסיסמה מוקלדת אינטראקטיבית** — לא בפקודה, לא בהיסטוריית ה-shell, לא במשתנה סביבה, ולא בשום דוח |
| Session Pooler (IPv4) | חיבור ישיר ל-DB עלול להיות IPv6-only |
| `-f /migrations/0031_...sql` | **קובץ מפורש, לא glob** — `*.sql` היה מריץ מיגרציות שכבר רצו |

* ⚠️ **אל תשתמשי ב-SQL Editor של Supabase Studio** — אין בו שליטה מפורשת
  ומוכחת על גבולות הטרנזקציה.
* כל מיגרציה בהרצה **נפרדת** (0031, ואז 0032) — לא בשרשור, ולא `*.sql`.
* `<PROJECT_REF>` ו-`<SESSION_POOLER_HOST>` הם placeholders. **אין לכתוב
  במסמך הזה host, project ref או סיסמה אמיתיים.**

**בכשל:** הטרנזקציה מתגלגלת אחורה מעצמה, **השער נשאר סגור**, ולא ממשיכים
לשלב הבא. לא "מתקנים ידנית וממשיכים".

### 2א.3 — סימון בהיסטוריה (`repair`) — רק אחרי הצלחה ואימות

**אין להריץ `repair` לפני שהמיגרציה עצמה הצליחה וה-verification שלה עבר.**
סימון מוקדם יוצר היסטוריה שקרית: הרשימה תטען שהמיגרציה הוחלה בזמן שלא.

```bash
# רק אחרי ש-0031 רצה בהצלחה ו-verification 0031 עבר:
supabase migration repair 0031 --status applied --linked
supabase migration list --linked          # אמת התאמה

# ובנפרד, רק אחרי ש-0032 רצה בהצלחה ו-verification 0032 עבר:
supabase migration repair 0032 --status applied --linked
supabase migration list --linked          # אמת התאמה
```

🔴 **אם המיגרציה הצליחה אך ה-`repair` נכשל:**
**אין להריץ שוב שום שינוי DB** — הסכימה כבר נכונה, והרצה חוזרת של המיגרציה
אינה הפתרון לבעיית היסטוריה. משאירים את **שער ההזמנות סגור**, ומתקנים
**אך ורק את היסטוריית המיגרציות** (בהתייעצות, כפעולה נפרדת).

**הרצה חוזרת בטוחה:** 0031 הוקשחה ב-9E.1 (`add column if not exists`,
`drop function if exists` לחתימות הישנות בלבד, `create or replace` לחדשות),
ו-0032 הייתה idempotent מלכתחילה. אין backfill ואין `UPDATE`/`DELETE` בשתיהן.
זו רשת ביטחון — לא היתר להריץ שוב במקום לחקור.

## 3. סדר ה-rollout — מחייב, ללא דילוגים

> ⚠️ **אין להניח ששינוי משתנה סביבה ב-Vercel משפיע בלי redeploy.** ערך
> חדש נקלט רק ב-deployment חדש. לכן סדר הצעדים למטה אינו שרירותי: קובעים
> את הדגל **לפני** ה-push, כך שה-deployment שנוצר מה-push כבר נולד עם
> השער סגור.

1. **preflight מקומי:** `npm run typecheck`, `npm run lint`,
   `npm run test` (ללא live), `npm run build` — כולם ירוקים.
2. **הגדר ב-Production: `NEW_BOOKING_SYSTEM_ENABLED=false`** (עדיין לא נכנס לתוקף).
3. **push של HEAD** → נוצר deployment חדש של הקוד החדש, **עם השער סגור**.
   ⚠️ **אין לטעון ש-redeploy של `origin/main` הישן לבדו סוגר את השער** —
   הוא אמנם מכיר את הדגל, אך הוא אינו הקוד שאנחנו פורסים, ופריסתו אינה
   חלק מהתוכנית. הצעד שמייצר את מצב "קוד חדש + שער סגור" הוא ה-push הזה.
4. **אמת שה-deployment הפעיל הוא בדיוק HEAD החדש** — לפי commit SHA
   ב-Vercel, לא לפי הנחה ולא לפי "נראה שעלה".
5. **אמת שהשער סגור, לפני שנוגעים ב-DB:** POST **סינתטי, ללא PII**
   לשני המסלולים (`/api/bookings/request`, `/api/appointments`) — שניהם
   חייבים להחזיר **403**.
   🔴 אם אחד מהם אינו מחזיר 403 — **עצור. אל תריץ מיגרציות.**
6. **`supabase migration list --linked`** (סעיף 2א.1) — 🔴 לא מסונכרן עד
   0030? **עוצרים, ולא מתקנים אוטומטית.**
7. **`0031` בטרנזקציה** — Dockerized psql, סעיף 2א.2 בדיוק.
8. **verification של 0031** (read-only): שתי הפונקציות קיימות בחתימה החדשה
   (14 ו-11 פרמטרים), **ובדיוק חתימה אחת לכל שם** (החתימה הישנה נעלמה —
   0031 אוכפת זאת בעצמה), והעמודות `privacy_notice_version` /
   `privacy_notice_acknowledged_at` קיימות ו-nullable.
9. **`repair 0031` + `list`** (סעיף 2א.3) — רק אחרי שצעד 8 עבר.
10. **`0032` בטרנזקציה נפרדת** — הרצה נפרדת, לא בשרשור עם 0031.
11. **verification של 0032** (read-only): `customers.retention_hold*` קיימות,
    ו-`get_crm_customer` מחזירה את המפתחות החדשים.
12. **`repair 0032` + `list`** (סעיף 2א.3) — רק אחרי שצעד 11 עבר.
13. **הגדר `NEW_BOOKING_SYSTEM_ENABLED=true`.**
14. **redeploy נוסף** כדי שהערך ייכנס לתוקף, ואמת שהוא אכן תפס.
15. **smoke tests** — סעיף 5.
16. **retention ו-Calendar נשארים dry-run בלבד**, וכל `execute` דורש אישור
    נפרד ומפורש (סעיף 6).
17. **scheduler — שלב נפרד לגמרי**, לא חלק מה-rollout הזה.

🔴 **אם ה-deploy בשלב 3–4 נכשל: אין להריץ שום מיגרציה ואין `repair`.** הפרודקשן הישן
(`origin/main` מול schema ≤0030) נשאר פעיל ותקין. מחזירים את הדגל ל-`true`
אם כיבית אותו, ומתקנים מחוץ לחלון.

## 4. תרחישי כשל

| **מיגרציה הצליחה אך `repair` נכשל** | 🔴 **אין להריץ שוב שום שינוי DB** — הסכימה כבר נכונה. משאירים את שער ההזמנות **סגור** ומתקנים אך ורק את היסטוריית המיגרציות. |
| **צריך להחזיר את ה-DB אחורה** | 🔴 **מוצא אחרון בלבד, ודורש אישור נפרד ומפורש של בעלת העסק.** להשתמש ב-SQL ה-rollback שהוכן בסעיף 2, ורק אם fix-forward אינו אפשרי. |
| **booking נכשל אחרי שהכול "הצליח"** | כבה מיד (`false` + redeploy), ובדוק בלוגי Supabase את קוד השגיאה. `PGRST202` = אי-התאמת חתימה, כלומר מיגרציה שלא רצה או רצתה חלקית. |

**🔒 בכל תרחיש: אין להציג ללקוחה הצלחה אם הבקשה לא נשמרה.** הקוד הקיים כבר
עומד בזה — כשל מחזיר 500 מפורש ("הבקשה לא נשמרה") עם הפניה לוואטסאפ, ושער
סגור מחזיר 403 מפורש. אין לשנות זאת ל"נראה בסדר" בשום מצב.

## 6. אחרי הפריסה — מה נשאר כבוי

- **`PRIVACY_RETENTION_SECRET` נשאר לא מוגדר.** ה-route מחזיר 404 וזו ברירת
  המחדל הרצויה בפריסה הראשונה.
- **אין scheduler.** לא Vercel Cron ולא QStash.
- **Calendar dry-run מותר רק אחרי** שאומת בפועל שאירוע חדש שנוצר בפרודקשן
  **אינו מכיל טלפון ב-description** — לא לפי commit, אלא לפי בדיקה בפועל.
  ר' `docs/calendar-phone-cleanup-runbook.md`.
- **Format A נשאר audit read-only**, והניקוי שלו ידני ע"י בעלת העסק.
- **🔒 אין `execute` — לא של retention ולא של Calendar — בלי אישור נפרד ומפורש.**
